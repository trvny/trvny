# Cloudflare Telegram assistant

- Keep the Worker small; prefer native `fetch` and platform bindings before dependencies.
- Reuse the existing Kanarek Companion model router through its same-account Service Binding; do not duplicate provider adapters or provider credentials here.
- Telegram is webhook-driven. Validate `X-Telegram-Bot-Api-Secret-Token` before parsing updates.
- Owner-only behavior must fail closed if owner IDs are missing or malformed.
- Keep durable `update_id` handling around Telegram send side effects; never blindly replay ambiguous delivery.
- Never commit bot tokens, webhook/ingest secrets, API keys, chat session data or `.dev.vars`.
- Long-term memory goes through the maintained Specialist Intelligence/Engram service boundary; the Telegram Worker must not own the Engram credential.
- Reuse the existing reminder/watch registry and scheduler; do not add a second cron-backed scheduling system for one feature.
- Third-party reply automation must remain separately opt-in, bounded and fail-closed. Draft-only stays the default; never automate consequential commitments or impersonate the owner.
- Heavyweight Legion/Hermes work goes through the scoped `PET_DISPATCHER` Service Binding/RPC surface. Do not add the operator control-plane bearer to this Worker or create a parallel task transport.
